Case 03 · Data engineering

Dynamic ETL Weather Dashboard 2.0

Stack: Python, Streamlit, SQLAlchemy, OpenWeather API, APScheduler Role: Solo build See it live → View repo →

The problem

My other cases each call a model once and show the result. I wanted a project that proved a different skill: a real ETL pipeline that runs unattended, on a schedule, against a live external API — extract, transform, load, and keep doing it every hour without anyone watching it.

What I did

Built a 3-stage ETL pipeline (extract.py → transform.py → load.py, orchestrated by pipeline.py) that pulls live weather for tracked cities from the OpenWeather API, cleans and enriches it, and writes it to a SQLite database via SQLAlchemy. A background scheduler (APScheduler) reruns the pipeline hourly on its own, and the Streamlit dashboard reads whatever's currently in the database — five tabs: live metrics, city comparison, 5-day forecast, trend analytics, and a geospatial map.

Real screen recording — multi-city dashboard, live on Streamlit Community Cloud, temperature/humidity trend charts across London, Karachi, New York, Dubai, Lahore, and Tokyo.

Three real bugs I had to actually understand, not just fix

Validation order bug: the transform step originally ran validation before feature engineering. Validation backfills missing values with the string "Unknown" — but pd.cut() (used to bucket temperature into Cold/Warm/Hot) crashes on a column of strings. If OpenWeather ever returned a response missing temperature or humidity, the whole pipeline would crash instead of degrading gracefully. Fix: feature engineering now always runs before validation, with a code comment explaining exactly why the order matters so I don't reverse it by accident later.

Timestamp crash on missing sunrise/sunset: OpenWeather doesn't always include sys.sunrise/sys.sunset depending on the station. datetime.fromtimestamp(None) raises a TypeError, which used to take down the whole ETL run for that city. Fix: a small _safe_timestamp() helper that returns None instead of crashing on missing or invalid epoch values.

Duplicate scheduler instances: Streamlit reruns the entire script on every user interaction, and session_state is per browser tab — so an early version that guarded the scheduler with if "scheduler_started" not in st.session_state let every new tab spin up its own separate BackgroundScheduler in the same process, each one independently hitting the weather API on its own hourly timer. Fix: a module-level flag shared by the whole process instead of a per-session one, so the job registers exactly once no matter how many tabs are open.

How it's built, no mystery code

etl/extract.py wraps the OpenWeather request in a requests.Session with automatic retries on 429/500/502/503/504 — so a transient API hiccup doesn't fail the whole city. etl/transform.py turns the raw JSON into a flat row (temperature, humidity, wind, clouds, coordinates), adds derived columns (temperature/humidity level buckets, day of week, hour), then validates. etl/load.py and database/repository.py handle writing to and reading from SQLite through SQLAlchemy models. scheduler/scheduler.py reruns the multi-city pipeline every hour in the background and, after each run, checks configurable thresholds (extreme heat, freezing, strong wind, high humidity) and can fire a webhook alert — but only the first time a threshold is crossed, not on every subsequent hourly check, so a multi-hour heatwave sends one notification instead of one every hour.

What came of it

A dashboard that keeps itself current without me touching it — refresh once, and the scheduler keeps pulling fresh data hourly from then on. It's also the first case on this site that isn't "call a model once," which was the actual point: proving I can build the unglamorous, always-running data plumbing underneath an AI product, not just the model-facing part.
