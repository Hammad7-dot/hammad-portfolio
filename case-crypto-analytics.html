Case 04 · Data engineering

Real-Time Crypto Analytics Platform

Stack: Python, PostgreSQL, Redis, FastAPI, Streamlit, Docker Role: Solo build Status: Local demo — not deployed View repo →

The problem

I wanted a project built the way a real team would run it — a written spec, a decision log, a blockers log — not just code that happens to work. Crypto prices move fast enough that "live dashboard" is a meaningful, checkable claim: either the numbers on screen are from the last few minutes or they aren't.

What I did

Built a 7-stage pipeline against a written spec: a connection-pooled Postgres layer (database.py), a CoinGecko extractor with retry/backoff (extract.py), a transform stage that cleans data and computes a volatility_score (transform.py), a batched upsert loader (load.py), an APScheduler orchestrator running every 5 minutes (etl_pipeline.py), SQL aggregation queries using window functions for ranking (analysis.py), and a Streamlit dashboard that auto-refreshes every 60 seconds and only ever reads from the database — never calls the API directly (dashboard.py).

Real screen recording — local run. Market cap, 24h price change, volume comparison, and volatility ranking, reading live from Postgres.

After the core 7 tasks, I added bonus extensions on top without touching their contracts: Redis caching for read queries (fails open if Redis is down), a FastAPI REST API over the same data, historical trend queries, Z-score anomaly detection, and Docker Compose to run the whole stack (Postgres, Redis, ETL, API, dashboard) with one command.

A real bug: the KPI that was silently wrong

The "Average Price" KPI card was actually computing .count() on the market_cap column — not AVG(current_price) — and the card was mislabeled "Average Market Cap" in the UI on top of that. It ran without erroring, which is exactly what makes this kind of bug dangerous: a wrong number that looks confident. Fixed by adding a proper analysis.average_price() query matching the pattern of the other analysis functions, relabeling the card correctly, and removing the leftover unused call — logged as DEC-006 in the decision log rather than just quietly patched.

How it's built, no mystery code

extract.py pulls the top 20 coins from CoinGecko with exponential backoff (2s/4s/8s) on 429s and 5xx errors. transform.py validates each record — missing required fields and out-of-range values (negative price/market cap/volume) are rejected as two distinct reasons, and every dropped record gets written to a dead-letter JSONL file with the full raw payload, not just summarized in a log line, so bad upstream data is actually inspectable later. load.py batches valid records into Postgres via ON CONFLICT upserts. A pipeline_runs table records every ETL cycle's stage reached, row count, duration, and error, so /health/etl and the dashboard's status banner reflect real pipeline health, not just "the dashboard loaded fine." cache.py wraps the analysis reads in Redis with a 55-second TTL — just under the 60-second dashboard refresh — but the real staleness guard is that the cache is explicitly invalidated after every ETL load, not the TTL itself.

The honest gap

Local-only — needs a running Postgres instance and, for the full stack, Redis. Not deployed anywhere public yet; the GIF above is a real local run, not a hosted demo. Anomaly detection needs at least 5 stored snapshots per coin (~25 minutes at the 5-minute polling cadence) before it flags anything, so it's not useful on a freshly started pipeline.

What came of it

The clearest proof yet that I can work from a written spec instead of just building whatever seems reasonable in the moment — and that I'll log a decision and fix a wrong number quietly sitting in a KPI card instead of leaving it, once I notice it's wrong.
